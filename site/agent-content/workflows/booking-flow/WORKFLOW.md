A booking ask that already names every detail (a spa slot, a table or a tour with its day, time, guests and name) skips the scenes: answer it at once with the step (5) BookingForm, pre-filled with what the guest said, never a read-back Card or DescriptionList and never a re-ask of a value you hold. A room booking runs on ONE surface transitioned scene to scene — create it once, then advance each step via updateComponents/updateDataModel on that SAME surface (never a fresh surface per step, never redeliver the root). The scenes, in order: (1) stay dates — ONE Calendar with mode "range" (valueStart/valueEnd bound two-way), NEVER two side-by-side calendars; (2) guests: ONE AmountPicker labeled "Guests" (min 1, max 8, step 1, no slider), committing through its own actionName with actionLabel "Continue", no sibling commit Button; (3) room & rate — a RadioGroup of room types with the nightly rate in each label, the recommended room preselected via the data model, plus a commit Button; (4) extras — independent Checkboxes (breakfast, spa credit, late check-out) each on its own data-model path, wrapped in a Column one per row, the commit Button a sibling AFTER the Column; (5) confirm before concluding: ONE BookingForm on that SAME surface, pre-filled for the guest to check; this form IS the booking's confirm step, so never a read-back Card or a separate ConfirmReceipt before the confirm. First write every value you hold with ONE updateDataModel on the draft path, then bind the form's value to that path, one field per detail (dateRange for a stay, Arrival and Departure in one field, or dateSingle for a one-day booking; time for a free arrival time, or radio for two to five fixed slots; select for a longer list such as the room or the treatment; stepper for guests, with min and max; text for the name; checkbox per extra), and its child is ONE confirm Button with submit true and the draft in its action context. Every scene after the first also carries a Back Button — an ordinary action beside Next/commit; Back and Next are scene transitions on the ONE still-open ask (never a new ask per step), and every draft answer lives under a shared "/draft/*" data-model prefix so nothing typed is lost when Back returns to an earlier scene. Only AFTER the user confirms: the closing turn SETTLES the booking with exactly one updateComponents on that SAME surface whose root becomes ONE ConfirmReceipt (a title such as "Booked", literal rows of {label, path} naming keys in the draft, never rows bound to a path, data bound to the draft, and status bound to a path holding "confirmed", so it shows as the settled receipt with no Back or Confirm), never a Badge on a Card, then the courtesy-close note with "flowEnd": true, same turn, no other UI. The scenes (1) to (4) each ask ONE thing on the room arc; a form that collects several booking details at once is always that ONE BookingForm. Never rebuild a booking form from primitives (Calendar, Select, RadioGroup, Slider, TextField). Never collect payment details.
