## 1 · Intent

One new module registers a `docx` extractor on the #1210 seam: read the `.docx` file as the zip it
is (EOCD → central directory → local header → payload), inflate `word/document.xml` via native
`DecompressionStream('deflate-raw')` (STORE passes through), walk the XML with namespace-aware DOM
queries (`w:t` run text concatenated, `w:p` → `\n`), and surface every malformed-input mode as a
`DocumentExtractionError` — never a hang, never an uncaught throw, never a silent empty string.
Zero new dependencies; fixtures are REAL minimal docx archives generated by a test-only builder.

## 3 · Module placement — `@agent-ui/app`'s `lib/`, sibling of the seam

`packages/agent-ui/app/src/lib/document-extraction-docx.ts`. Reasons, stated:

- The extractor exists solely to register on `document-extraction.ts`, which lives in this folder;
  the seam's own header comment names exactly this move ("docx (GH #1214) … register their own
  extractors later by calling `registerDocumentExtractor` from their own modules").
- `app` is a top-tier DAG consumer — nothing imports upward into it, so a parser living here can
  never leak into `components`/`a2ui`/catalog surfaces. Hoisting the zip reader to `shared` (or a
  new package) would generalize a single-consumer parser with zero second consumer — the same
  judgment that kept `zip-writer.ts` a local site lib rather than a package. If a second consumer
  ever appears, hoisting is a mechanical later move; pre-hoisting is not.
- `site/lib/zip-writer.ts` is NOT imported (site code is above packages in the DAG; app importing
  site is an upward import). The reader re-declares the four signature constants — mirroring the
  writer's names (`LOCAL_FILE_HEADER_SIG` · `CENTRAL_DIRECTORY_SIG` · `END_OF_CENTRAL_DIRECTORY_SIG`
  · `STORE_METHOD`, plus new `DEFLATE_METHOD = 8`) and its field-table comment style, so the two
  files review as the two halves of one format.

`test(file)`: extension `docx` (the seam's `extensionOf` pattern) OR MIME
`application/vnd.openxmlformats-officedocument.wordprocessingml.document`. `name: 'docx'`. LIFO
registration means it out-precedes the txt fallback automatically; a `text/*` file still routes to
txt (test asserts both directions).

## 4 · Algorithm

`run(file)` = `extractDocxText(new Uint8Array(await file.arrayBuffer()))`. Whole-buffer is correct
here, not a shortcut: the seam already rejects >10MB (`MAX_RAW_FILE_BYTES`) BEFORE `run` is called,
so the buffer is bounded by contract. All multi-byte reads are little-endian `DataView` gets.

**4.1 EOCD scan (bounded tail).** The EOCD record is 22 bytes + a comment of 0–65535 bytes, so the
signature `0x06054b50` lives somewhere in the last `22 + 65535` bytes. Scan BACKWARD from
`len - 22` down to `max(0, len - 22 - 65535)` — a spec-true hard bound, never a whole-file scan, so
pathological input costs at most ~64KB of byte comparisons (no hang, C6 asserts prompt rejection).
A candidate offset is accepted only if its comment-length field equals exactly the bytes remaining
after the fixed record (`commentLen === len - (pos + 22)`) — this disambiguates a stray signature
byte-pattern inside the comment or archive data. No valid EOCD in the window → `'corrupt-document'`
("not a zip archive").

**4.2 Central-directory walk.** From EOCD read `entryCount` (u16 @8, total-entries field),
`cdSize` (u32 @12), `cdOffset` (u32 @16). Bounds gate first: `cdOffset + cdSize <= eocdPos`, else
corrupt. Walk up to `entryCount` entries from `cdOffset`: verify per-entry signature `0x02014b50`;
read `gpFlags` (@8), `method` (@10), `compressedSize` (@20), `uncompressedSize` (@24), `nameLen`
(@28), `extraLen` (@30), `commentLen` (@32), `localHeaderOffset` (@42); decode the name as UTF-8
(`TextDecoder` — we only ever compare against the ASCII string `word/document.xml`, so the
GP-bit-11 cp437/UTF-8 distinction is irrelevant); advance by `46 + nameLen + extraLen + commentLen`
with a bounds check on every step (an entry running past `cdOffset + cdSize` → corrupt). Stop at
the first `word/document.xml` (exact match; docx never uses `\` separators or a leading `/`). Walk
completes without finding it → `'corrupt-document'` ("no word/document.xml — not a docx").

**4.3 Local header → payload.** At `localHeaderOffset`: verify `0x04034b50`, read the LOCAL
header's OWN `nameLen` (@26) and `extraLen` (@28) — the load-bearing subtlety this section exists
for: real producers (Word) put extra fields in the local header that the central directory doesn't
mirror, so the payload offset is `localHeaderOffset + 30 + localNameLen + localExtraLen`, never a
CD-derived number. Sizes, conversely, come ONLY from the central directory — which also makes GP
bit 3 (data-descriptor entries, whose LOCAL size fields are zero) work with no special handling.
Bounds check `payloadStart + compressedSize <= len`, else corrupt. Reject up front: GP bit 0 set
(encrypted) → corrupt-document with an "encrypted" message; `0xFFFFFFFF`/`0xFFFF` sentinel values
(zip64) → corrupt-document (a 10MB-capped file never legitimately needs zip64 — §8).

**4.4 Inflate.** `method === 0` (STORE) → the payload slice as-is. `method === 8` (DEFLATE) →
`new Response(new Blob([slice]).stream().pipeThrough(new DecompressionStream('deflate-raw'))).arrayBuffer()`
wrapped in try/catch; any rejection (garbage bytes, truncated stream) → `'corrupt-document'`. Any
other method → `'corrupt-document'` naming the method number in the message — real docx producers
emit only 0 and 8 (F2's grounding), so a userland inflate fallback or further methods are
deliberately out (§8). CRC-32 is NOT verified (§8).

**4.5 DOMParser walk.** Decode UTF-8, `new DOMParser().parseFromString(xml, 'application/xml')`.
Parse-failure detection: `doc.getElementsByTagName('parsererror').length > 0` — the WHATWG-specced
failure shape is a parsererror element IN the returned document (never a throw), and
`getElementsByTagName` matches the prefix-less qualified name regardless of which namespace the
engine puts it in (Chrome ≠ Firefox here); **probe-verified under this repo's jsdom 2026-08-18**:
malformed XML → returned doc with parsererror count 1, no throw. Then guard the root:
`documentElement.localName === 'document'` in the OOXML namespace
`http://schemas.openxmlformats.org/wordprocessingml/2006/main`, else corrupt (this is what makes
"valid XML that isn't WordprocessingML" a VISIBLE failure instead of a silent empty string). Walk:
`doc.getElementsByTagNameNS(W_NS, 'p')` in document order (OOXML never nests `w:p` in `w:p`, so
per-paragraph scoping double-counts nothing — table cells' paragraphs arrive in order too); per
paragraph, concatenate `textContent` of `p.getElementsByTagNameNS(W_NS, 't')` (this natively honors
`xml:space="preserve"` spacing); join paragraphs with `\n`. **Ruled by the same probe** (the
dispatch's named uncertainty): `getElementsByTagNameNS(W_NS, 't')` → 3/3 hits under jsdom;
`querySelectorAll('w\\:t')` → **0 hits** — CSS selectors are OUT for namespaced XML, no builder
re-litigation. A validly parsed, root-verified document with zero paragraphs returns `''` honestly
(a genuinely empty docx is empty, not corrupt).

## 5 · Failure modes → `'corrupt-document'`, one new union member

Add exactly one member: `DocumentExtractionErrorReason = 'too-large' | 'unsupported-type' |
'corrupt-document'`. Reusing `'unsupported-type'` is rejected — that reason means "no extractor
claimed the file", and the R1 AC ("visible reason") requires the chip to say something different
for "claimed .docx, bytes don't deliver". The name is deliberately format-generic (not
`'corrupt-docx'`) so the pdf extractor (#1215) reuses it instead of minting a fourth member. Every
in-extractor failure maps to it, with the specific diagnosis in `message` (callers branch on
`reason`, never re-parse `message` — the seam's own law): no EOCD in the bounded window ·
CD/local-header bounds or signature violation · zip64 sentinels · encrypted entry · missing
`word/document.xml` · unsupported method · `DecompressionStream` rejection · XML parsererror ·
wrong root element/namespace. Integration check done at plan time: the only `reason` branch in the
repo is the `agent-admin.ts:2902` ternary (not an exhaustive switch — nothing breaks at compile
time), and C3 upgrades its copy so a corrupt file stops reading as "unsupported file type".
`run()` re-checks no budgets — the seam owns both ends (R6).

## 6 · Fixtures — generated at test time, zero committed binaries

`docx-test-fixtures.ts` (C5) builds REAL minimal docx archives: `[Content_Types].xml`,
`_rels/.rels`, `word/document.xml` — a valid, Word-openable document (that satisfies the AC's "real
minimal fixture"; "real" = spec-conformant archive a real consumer opens, not "committed binary").
Ruling — generate, don't commit, because: (a) fixtures stay reviewable TypeScript, not opaque blobs
in git; (b) the DEFLATE fixture compresses at build time via native
`CompressionStream('deflate-raw')` — a byte-true producer of exactly the stream the reader must
inflate, available under both gates; (c) malformations are surgical knobs, not hex-edited files;
(d) a committed Word-produced binary would exercise the local-extra-field divergence only by luck —
the builder's knob exercises it deterministically. Knobs: per-entry `method` (STORE / DEFLATE /
arbitrary override for the unsupported-method case) · trailing EOCD comment bytes · a local-header
extra field ABSENT from the CD entry (the §4.3 divergence) · truncate-at-byte-N. Negative fixtures:
plain-text bytes, a PNG 8-byte magic header, a valid archive missing `word/document.xml`, a DEFLATE
entry with garbage payload bytes, valid zip + non-XML document.xml, valid XML + wrong root ns.

## 7 · Test plan + gate split

**Gate decision (explicit, per dispatch): `npm test` (jsdom) is THE module gate; `test:browser`
carries exactly ONE surface-level round-trip (C7), nothing module-level.** Grounding: under this
repo's vitest/jsdom/Node 24 config, `DecompressionStream` is Node's REAL native implementation
leaking through the environment merge and `DOMParser` is jsdom's real XML parser — both
probe-verified executing (not skipped) 2026-08-18. A pure byte/XML parser has no rendering, focus,
or layout surface, so re-running the same assertions under Chromium is redundant proof and shard
budget spent for nothing. What jsdom genuinely cannot prove — the browser-native
DecompressionStream + DOMParser + attach path + entry mint composing on a real engine — is exactly
the ticket AC's browser sentence, and C7 proves precisely that, once.

`document-extraction-docx.test.ts` (C6, jsdom):
- Capability gate: `describe.skipIf(typeof DecompressionStream !== 'function')` with a named reason
  (portability only) PLUS one ungated canary test asserting `DecompressionStream` IS defined under
  this repo's config — so a future vitest/jsdom config change that would silently skip the whole
  suite fails LOUD instead.
- Positive: STORE fixture round-trip through `extractDocumentText` (full seam: text + `meta.extractor
  === 'docx'`) · DEFLATE fixture (the inflate path) · local-extra-field variant · trailing-EOCD-comment
  variant · multi-entry archive with `word/document.xml` not first · paragraph/run mapping (two `w:p`
  → `\n`-joined; multiple `w:t` incl. `xml:space="preserve"` concatenated).
- Negative (each: `rejects.toMatchObject({ name: 'DocumentExtractionError', reason:
  'corrupt-document' })`, resolving promptly — vitest's own timeout is the no-hang proof): non-zip
  text bytes · PNG header · truncated central directory · missing `word/document.xml` · garbage
  DEFLATE payload · unsupported method · malformed XML · wrong root namespace.
- Registry: `.docx` routes to `docx` ahead of the txt fallback; `text/plain` still routes to `txt`;
  the `afterEach` reset/re-register pattern from `document-extraction.test.ts` extended to re-register
  both extractors.

`document-ingest-docx.browser.test.ts` (C7, real engine): one generated docx `File` driven through
the shipped attach path → assert the resource entry holds the extracted text (R1's browser AC).
Builder confirms which of the six shards globs it and keeps it to this one test — never a second
module suite (the shard-splitting law).

## 8 · Rejected alternatives

- **mammoth.js / any npm unzip or docx lib** — F2 ruled zero-dep feasible and rejected mammoth
  (~600KB) by name; the ticket's AC is "ZERO new deps". Not a fallback either (see freeze note).
- **zip64** — sentinel values → corrupt-document. The seam caps input at 10MB; a legitimate zip64
  docx cannot reach this code.
- **Encrypted entries (GP bit 0)** — corrupt-document with an "encrypted" message; never a crypto
  implementation. (No real-world docx knowledge base is zip-encrypted; a password-protected Word
  file is a different container entirely and simply fails visibly.)
- **Userland DEFLATE fallback for pre-Baseline-2023 engines** — the repo's support floor is Baseline
  2023 (F2 pins `'deflate-raw'` availability); a hand-rolled inflater is a huge correctness surface
  for engines this project doesn't target. The defensive capability gate in tests is portability
  courtesy, not a support commitment.
- **CRC-32 verification** — the reader's consumer is a text extractor, not an archiver; a corrupted
  payload surfaces as a DecompressionStream rejection or XML parsererror anyway (both →
  corrupt-document). Skipping CRC drops ~zero safety and keeps the reader honest about its job.
  (The writer has `crc32` because WRITING a valid archive requires emitting it.)
- **`w:tab`/`w:br` → whitespace mapping, headers/footers, footnotes, multi-part docx** — out of v1;
  the ticket's mapping is `w:t` + `w:p` exactly. Losing a tab inside a run is acceptable text-
  extraction fidelity for prompt knowledge; revisit only on a real complaint.
- **Committing a binary Word-produced fixture** — §6's ruling (generated fixtures win on review-
  ability, determinism, and deliberate malformation control).
- **A streaming/chunked reader** — pointless under a 10MB pre-enforced cap; whole-buffer is simpler
  and bounds-checkable in one place.

## 9 · Risks / notes for the builder

- **`Blob.stream().pipeThrough(DecompressionStream)` under jsdom** — the probe verified the
  constructors exist; the full pipe composition (jsdom `Blob` + Node streams) is expected to work
  but is the first thing C6's DEFLATE test proves. If jsdom's `Blob.stream()` and Node's
  `DecompressionStream` refuse to compose, the fallback INSIDE the same contract is feeding the
  slice via a manual `ReadableStream` of one chunk (pure spec API, no new dep) — builder may make
  that swap without a plan repair; anything beyond it is a handback.
- **`source-bytes.test.ts` / bundle trip-wires** — C5 is test-only and imported by no src barrel;
  if any size/byte gate counts it, the fix is exclusion by the gate's own existing convention, not
  moving the fixture builder into a test file body.
- Non-decision recorded (no ADR): nothing here forks an architectural alternative — F2 already
  ruled mechanism and zero-dep law; this LLD only concretizes module layout + algorithm, so the
  ADR default-no holds.
