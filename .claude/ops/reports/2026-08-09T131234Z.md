## Evidence for #613 (per the standing evidence-first ruling)

This firing's `git branch -r` (pre-prune) showed `origin/task/624-nav-polish` still present —
initially read as a possible new survivor matching #613's pattern. **Investigated before treating
it as one:**

1. `campaign_close.py 625`'s own C2 check (a live `git ls-remote --heads origin` call, not a
   cached ref) reported the branch **already absent** at time of running.
2. `git fetch --prune origin` then confirmed: `- [deleted]  (none) -> origin/task/624-nav-polish`
   — i.e., the branch really was gone on the remote; the earlier `git branch -r` output was
   reading this checkout's **stale local remote-tracking ref**, left over from before PR #625's
   merge-time delete, never pruned in this checkout until just now.

**Conclusion: this is NOT a new #613 survivor.** The remote-side delete at merge time worked
correctly for #625/`task/624-nav-polish` — the apparent survival was a local-ref staleness
artifact in the sweep's own checkout, not a repeat of the silent-failure class. Worth recording as
a data point regardless: it demonstrates that `git branch -r` alone (without a preceding
`git fetch --prune`) is not sufficient to classify a branch as a real survivor — a lesson for this
agent's own procedure as much as for #613's root cause. No verbatim `gh pr merge` output was
captured for #625 (it was merged in a prior session, not this sweep), so this data point doesn't
resolve #613's checked-out-in-worktree-vs-not variable either way.

**Proposed, not executed:** post this finding as a dated comment on #613 (a non-event that still
refines the evidence trail — this firing's own local-ref-staleness confound is worth the tracker
knowing about so a future firing doesn't misclassify the same artifact as a real survivor). Not
posted directly — GH issue comments are outside this agent's three gated actions.
