## Findings
- step 1: interfaces: the `offline.ts` environment rule is false in plain Node. The Do says "Detect jsdom by no `navigator`, or a `navigator.userAgent` that contains `jsdom`" and that Node throws for every URL (planner-L3-2.md:53-55). Node has a global `navigator` and no `location`, so the stated rule sends plain Node down the real-browser branch, which reads `location.origin`. That path is load-bearing for `kit.ts selftest` under `node --experimental-strip-types` (planner-L3-2.md:283, :332) and for the node-environment `tools` tests `load.test.ts` and `kit.test.ts` (planner-L3-2.md:268, :292). A builder must either break those or deviate from the stated rule. Evidence: `node -e 'console.log(typeof navigator, JSON.stringify(globalThis.navigator?.userAgent), typeof location)'` prints `object "Node.js/24" undefined` on v24.9.0.
- step 1: builder readiness: the scenario format is not settled, and the strict parser makes its closed field set load-bearing. `scenario.ts` takes "`ScenarioTurn` and `TurnExpect` as in the architect file" (planner-L3-2.md:37) and must reject unknown fields by JSON path (planner-L3-2.md:39). The architect file gives only field names, `TurnExpect { heal?, verdict?, produce?, tree?, bindings?, clientMessages?, dataModel?, tools? }`, with no shape for any of them (architect-L1.md:35). The decompose leaf `n_format` adds none (decompose/manifest-v1.json, `n_format` accept). The step 1 builder has to design eight expectation sub-schemas that steps 2 to 5 consume.
