## Approach

The scattered inventories are already each derived from one owning source and each gated in place: descriptors drive the site, llms-full and the dogfood inventory; `catalog.json` drives the prompt inventory (ADR-0071) and the renderer; `selection.json` drives the selection clause (ADR-0232); mini-skills and genui packs glob their own directories; the persona fragments compose into derived `base--persona` catalogs at registration time. What is missing is the join: nothing relates a catalog type to the control it renders, a preset to the fragment it selects, a mini-skill or corpus record to a catalog that exists, or a persona to the capabilities its turn can actually use. Those joins are exactly what today fails silently: `resolveEffectiveCatalogId` falls back to the base when a preset's `localPatterns` names no registered fragment, `selectMiniSkills` and `retrieve` filter on an exact `catalogId` so a derived catalog retrieves nothing, and catalog exclusion has two truths (`EXCLUSION_ALLOWLIST` test-local in `default/index.test.ts:179`, and a `catalog: excluded` line in `command-modal.md`).

The design is a derived index, never a source (ADR-0173 cl.5 stays: no catalog row is generated), living in `@agent-ui/a2ui`, the only package allowed to know both components and catalogs. It has two tiers. The runtime tier composes from objects every host already holds (the `Catalog` map, `SelectionGuidance`, `MINI_SKILLS`), so the Worker needs no new asset and no new `NODE_ALLOWED` entry; the build tier adds what only disk knows (descriptor tier and description, the components registry from #1814, prompt assets, corpus shards, T-0012's persona manifest). A pure module `src/registry/` (new `./registry` subpath, zero `node:*`) owns the row model, `composeRegistry(sources)`, `registryViewFor(registry, catalogId)` with the same first-`--` split `selectionGuidanceFor` uses, `retrievalScopeFor(catalogId)`, the one pure tag rule (pascal plus the `ui-audio` rename plus the `Option`/`MenuItem` nulls, which T-0008 imports when it builds), and `selectCapabilities(intent, view, cap)` over the existing `corpus/text-similarity.ts` ranker. A Node loader and CLI under `tools/registry/` read sources by `readFileSync` (a persona `manifest.ts` cannot be imported under plain Node: `ERR_IMPORT_ATTRIBUTE_MISSING`, probed) and write one committed projection, `site/capability-registry.json` plus its `site/public/` twin (the sitemap two-copy vehicle), drift-gated by regenerate-and-compare. The projection exists because the browser site cannot read the Node-only sidecars and mini-skills, and because Kim's stated pain is "nothing is one queryable index"; its tax is a regen on every descriptor, catalog, sidecar or mini-skill edit, the same tax sitemap and llms-full already carry.

Consumers wire in this order. Wiring checks first: a jsdom gate proves the pure tag rule equals `WidgetFactory.tag` (and every `VariantDispatch` variant) across base and persona factories, every `ui-*` type resolves to a components registry record, every preset `localPatterns` resolves to a shipped fragment, every mini-skill and corpus `catalogId` is registered, and exclusion reads one extracted allowlist. Evals next: T-0005's per-persona leg reads `registryViewFor(derivedId)` (notFor edges plus persona-only types) instead of the sidecars directly. The site page renders the per-persona view and joins `TIER_OF`/`NESTED_ONLY` page-side (site-owned, a2ui cannot import them). Prompt retrieval last, in two forked steps: widening retrieval scope to the base is a SPEC-R6 (persona-catalog-composition) amendment, and a pruned per-turn inventory moves prompt bytes and waits for T-0003's section trace and T-0005's evals; the registry ships the pure functions both need and leaves the composition untouched, so the default prompt stays byte-identical.

## Rejected alternatives

- One registry inside `@agent-ui/components` spanning descriptors and catalogs: layering forbids components knowing a2ui (already rejected by the #1814 architect).
- Generating catalog rows or sidecar entries from the registry: ADR-0173 cl.5 rules catalog content hand-curated; the registry indexes only.
- A Node loader under `src/agent/` with a Worker shim entry: no runtime consumer needs descriptor-derived fields; the Worker composes the runtime tier from the catalog map and sidecars it already holds, so a sixth `NODE_ALLOWED` entry and a new `FILES` key buy nothing.
- Reading `agent-admin-presets.ts` textually for persona rows: brittle regex over site TypeScript; T-0012 is building the one Node-safe persona source.
- Per-persona `registry.gen.json` beside each fragment: a fifth persona file T-0012 does not know about; runtime composition over the manifest replaces it, and the committed projection carries the persona rows instead.
- Including skills, agents and the ADR index as rows: dev harness, not shipped; `adr-index.json` is already generated by `generate-sitemap.mjs:279` and skill/agent wiring is already checked by `claude_wiring_check.py` and `harness_wiring_check.py`; no prompt, renderer or eval reads them (fork 4, recommend out).
- Pruning the prompt inventory per turn in this ticket: moves the byte-pinned baselines per query and cannot be judged before T-0003's section sizes and T-0005's selection evals exist (fork 1, recommend defer).
- A descriptor-side `intents`/`notFor` field: rejected by ADR-0232 and the T-0008 architect; two sources that drift.
- Keeping `EXCLUSION_ALLOWLIST` test-local and re-deriving exclusion in the loader: a second derivation of the same truth (the GH #346 root cause).

## Risks

- Fork 2 cost: with base exemplars retrieved for `agent-ui--croupier`, the few-shot JSONL shows `"catalogId":"agent-ui"` while `catalogIdTeaching` demands the derived id on the same prompt; `stampCreateSurfaceCatalogId` keeps the wire correct but the prompt contradicts itself. Kim rules with that trade stated.
- T-0012 ships a manifest that is not plain-Node-loadable (a `.ts` importing `catalog.json` without the attribute): the CLI cannot run under Node and generation falls back to a vitest writer (the `recapture-baseline.test.ts` precedent), a worse ergonomic.
- #1814 changes the components registry shape or name before wave 4: the loader's fleet join and the accept predicates must be re-pinned against the landed artifact.
- The pure tag rule diverges from `WidgetFactory.tag` for a future variant-dispatch type; the parity gate reds, which is intended, but the fix must land in the rule, never in a per-type alias.
- The committed projection drifts constantly during the barrel migration (descriptor edits across 79 folders): schedule generation after wave 3 lands, as the rollout already orders.
- The concurrent `asset-embed` architect designs discovery that does not read the registry's asset rows; then the `prompt-asset` kind has only the `shim` consumer gate and should be dropped rather than kept as decoration.
