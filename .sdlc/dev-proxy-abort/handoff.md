## Goal
When the browser disconnects from the Node dev proxy mid-turn, the turn is aborted: the upstream provider stream and in-flight tool calls are cancelled, as the production Worker already does with `request.signal`. Tracks GH #1797, gap (a) of (a) to (d); this task is only (a).

## Context
Verified gap (code reading, 2026-10-05): `packages/agent-ui/a2ui/tools/agent/dev-proxy-plugin.ts` has two turn paths that pass no turn-level `AbortSignal`:
- the prose `/chat` arm (about lines 325-345): `buildToolDispatch(active, env)` then `providerDispatch.provider.stream({ ..., ...toolOpts })`; a comment says "No turn-level AbortSignal exists on this Node route";
- the produce arm (about lines 398-450): `buildToolDispatch(active, env)` then `produce(input, deps, { maxRounds: 3, ... })` with no `signal`.
The Worker (`tools/agent/worker/index.ts`, about lines 194, 204, 278, 296) already does `buildToolDispatch(active, hostEnv, request.signal)` and passes `signal: request.signal` into `produce`. `produce.ts:1059` forwards `opts.signal` to the provider; `anthropic.ts` passes `req.signal` to `fetch` and to `req.executeTool`; `tool-dispatch.ts:66` uses `callSignal ?? signal`; built-in fetch tools and the MCP client combine it with their own 10 s timeout via `AbortSignal.any`. So only the Node proxy lacks the signal. No `AbortController` exists in `dev-proxy-plugin.ts`.

Design to confirm against the code (do not assume): create one `AbortController` per request in each of the two paths, abort it when the client connection closes before the response finishes (`res.on('close')` with a `res.writableEnded` check, or `req.on('aborted')`/`close` as the Node version requires), pass `controller.signal` to `buildToolDispatch(active, env, signal)` and to `produce(..., { signal })` and to `provider.stream({ signal })` if its request type has a `signal` field (check `AgentProvider`/stream request types). A normal completed response must NOT abort (no false abort after `res.end`). When aborted, the loop's own error path must not write to a closed response or throw an unhandled rejection; the existing catch writes a terminal error line only if the response is writable. Update the two stale comments that say no signal exists.

Add a deterministic test that proves the abort: build the plugin's middleware with fake `req`/`res` EventEmitters and a stub provider whose `stream` records `req.signal` and awaits it, emit `close` on `res` before completion, and assert the provider's signal becomes aborted and the handler settles without throwing; add a negative control (complete normally, then emit `close`, signal stays unaborted).
